# STM32 二自由度云台 · 蓝牙无线控制

基于 **STM32F103C8T6 + MPU6050 + HC-05** 的双轴云台，从零手写实现体感遥控、电位器遥控、以及带按键切换的多模式版本。

> 全部使用 **STM32 标准外设库（SPL）+ Keil MDK5**，裸机开发，无 RTOS。

## 项目概览

整个系统分成**发送端（遥控器）**和**接收端（云台）**两块板，通过两个 HC-05 蓝牙模块做单向透传：

```
┌──────────── 发送端 ────────────┐            ┌──────────── 接收端 ────────────┐
│                                │            │                                │
│  MPU6050 ──I2C2(PB10/11)──┐    │            │    ┌──TIM2_CH1(PA0)── 舵机 X    │
│                            │    │            │    │                            │
│  电位器×2 ─ADC(PA1/PA2)────┼───►│  USART1    │    └──TIM2_CH2(PA1)── 舵机 Y    │
│                            │    │  PA9/PA10  │                                │
│  按键×2 ──(PA4/PA6)───────┘    │    │       │  USART1(PA9/PA10) ◄────────────┤
│                                │    ▼       │                                │
│  OLED(PB8/PB9)                 │  HC-05 ────┼──► HC-05                       │
└────────────────────────────────┘            │  OLED(PB8/PB9)  LED×3(PA5/6/7) │
                                              └────────────────────────────────┘
```

发送端负责**采集 → 映射 → 滤波 → 打包 → 发送**；
接收端负责**解帧 → 目标角 → 平滑限速 → PWM 输出**。

**核心设计思路：** 无论数据源是 MPU6050 还是电位器，最终都归一化成「两个 0~180° 的舵机目标角」，所以接收端完全不需要知道数据来自哪种传感器 —— 这也是后来能把两套单功能版本合并成多模式版本的基础。

## 三个版本对比

| | `02-mpu6050-gimbal` | `03-pot-gimbal` | `01-multimode-gimbal` |
|---|---|---|---|
| **控制方式** | 体感（倾斜模块） | 旋钮（两个电位器） | **两者合一，按键切换** |
| **发送端数据源** | MPU6050 加速度 → `atan2f` 求倾角 | ADC 12bit → 线性映射 | 按 `currentMode` 分派 |
| **姿态解算** | `roll = atan2f(ay, az)`<br>`pitch = atan2f(-ax, √(ay²+az²))` | — | 同左 |
| **发送端滤波** | 一阶低通 α = 0.3 | 一阶低通 α = 0.6 | 两套参数独立 |
| **帧格式** | `FF … FE` 6 字节 | `FF … FE` 6 字节 | `AA 55 LEN CMD DATA` 8 字节 |
| **模式切换** | — | — | 按键 KEY1 = 体感<br>按键 KEY2 = 电位器 |
| **接收端** | 平滑控制 + OLED + LED | 同左 | 同左 + 模式指示灯 |

### 为什么保留三个版本

单功能版本是**学习过程的快照**，多模式版本是**重构后的结果**。放在一起可以对比出：

- 帧格式为什么要从「固定 6 字节」演进到「帧头 + 长度 + 命令码」
- 为什么要把「数据源」抽象出来，而不是复制两份主循环
- 多模式带来的状态管理问题（切模式时滤波器要从旧值对齐，否则舵机会弹跳）

| 器件 | 型号 | 数量 | 说明 |
|---|---|---|---|
| 主控 | STM32F103C8T6 最小系统板 | 2 | Cortex-M3 @72MHz，64KB Flash / 20KB RAM |
| 姿态传感器 | MPU6050 (GY-521) | 1 | 六轴，I²C 接口 |
| 蓝牙模块 | HC-05 | 2 | 一主一从，经典蓝牙 SPP 透传 |
| 舵机 | MG90S | 2 | 金属齿轮，行程 180° |
| 显示屏 | 0.96" OLED SSD1306 | 2 | 128×64，I²C |
| 电位器 | B10K 旋转电位器 | 2 | 接 3.3V，**不可接 5V** |
| 按键 | 轻触开关 | 2 | 内部上拉，低电平有效 |
| 调试器 | ST-Link V2 | 2 | SWD 下载 |

### ⚠️ 供电注意

**舵机必须用独立 5V 电源（建议 5V/3A），并与主控共地。**

两个 MG90S 堵转电流可达 1.5A 以上，直接用开发板的 3.3V/5V 引脚供电会导致：主控复位、蓝牙断开、舵机抖动。面包板上的 MB102 电源模块只有 0.7A，**带不动两个 MG90S**。

建议在舵机电源两端并联 **470~1000µF 电解电容**吸收瞬间电流冲击。

## 通信协议

### 协议演进

**第一代（单功能版本）** —— 固定长度，无类型标识：

```
┌──────┬────────────┬────────────┬──────┐
│ 0xFF │ S1L  S1H   │ S2L  S2H   │ 0xFE │
└──────┴────────────┴────────────┴──────┘
  帧头    舵机1角度    舵机2角度    帧尾      共 6 字节
```

- 角度放大 100 倍用 `int16` 传输（分辨率 0.01°）
- **小端序**（低字节在前）
- 无校验

**第二代（多模式版本）** —— 引入帧头、长度、命令码：

```
┌──────┬──────┬──────┬──────┬──────────────┐
│ 0xAA │ 0x55 │ LEN  │ CMD  │  DATA[0..N-1]│
└──────┴──────┴──────┴──────┴──────────────┘
  帧头1  帧头2   长度   命令      数据          共 4+LEN 字节
```

| 字段 | 长度 | 作用 |
|---|---|---|
| `0xAA 0x55` | 2 | 双字节帧头，误同步概率降到 1/65536；`0xAA`/`0x55` 位模式互补，便于位同步 |
| `LEN` | 1 | 数据字节数（1~64），接收端据此决定收多少 |
| `CMD` | 1 | 命令码，接收端据此分派解析函数 |
| `DATA` | N | 载荷 |

**当前 CMD 用法：** 多模式版本里 `CMD` 直接承载「当前模式」（0 = 体感，1 = 电位器），接收端用它同步显示与 LED。

### 一帧的实际字节（8 字节）

```
AA 55 04 00 12 03 4B 02
│  │  │  │  └──┬──┘
│  │  │  │     └── 舵机1=0x0312(786) 舵机2=0x024B(587)  → 7.86° / 5.87°
│  │  │  └── CMD = 0x00（体感模式）
│  │  └── LEN = 4
│  └── 帧头2
└── 帧头1
```

### 接收端状态机

```
state 0 ──0xAA──► state 1 ──0x55──► state 2 ──LEN──► state 3 ──收满──► 完成
                    │                 │                │
                    └──非0xAA─────────┴────────────────┴──► state 0
```

## 滤波与平滑算法

系统里有**两级**处理，分工不同：

### 第一级：发送端一阶低通（抑制传感器噪声）

```
y[n] = y[n-1] + α · (x[n] - y[n-1])
```

| 版本 | α | 说明 |
|---|---|---|
| 体感 | 0.3 | MPU6050 加速度噪声较大（±1~2 LSB） |
| 电位器 | 0.6 | 电位器噪声只有 ±0.09°，可以用更大的 α 换来更快响应 |

**时间常数**：`τ = α·T / (1-α)`，`T` 为采样周期。α 越小越平滑、但滞后越大。

### 第二级：接收端变步长限速（保护舵机 + 消除微抖）

```c
Diff = Target - Actual;
if (|Diff| > Deadzone) {          // 死区 0.5°，吃掉静止时的抖动量
    Step = DecideStep(|Diff|);    // 0.5° → 6.0° 之间连续插值
    Actual += (Diff > 0) ? Step : -Step;
}
```

`DecideStep` 做的是**分段线性插值**：

| 差值范围 | 步长 |
|---|---|
| < 5° | 0.5°/帧（慢速精细） |
| 5° ~ 15° | 线性过渡 |
| > 15° | 6.0°/帧（快速跟随） |

**为什么不用固定步长：** 固定步长小则大角度动作慢，大则小角度动作过冲、抖动。

**为什么必须有死区：** 传感器噪声和蓝牙误码会让目标角持续微动，没有死区舵机会一直「嗡嗡」响并发热。

### 姿态解算

```c
roll  = atan2f(ay, az) * 57.29578f;   // 弧度转角度
pitch = atan2f(-ax, sqrtf(ay*ay + az*az)) * 57.29578f;
```

**必须用 `atan2f` 而不是 `atan(x/y)`：**

- `atan(x/y)` 在 `y = 0` 时除零，且丢失象限信息（±180° 会混淆）
- `atan2f(y, x)` 内部处理符号，全量程 −π~+π 无死角

倾角限幅 ±30°，再线性映射到舵机的 0~180°：

```c
S1_Angle = 3.0f * (ThetaX + 30.0f);   // -30~+30° → 0~180°
```

```
<工程>/
├── Project.uvprojx         Keil 工程文件
├── Start/                  CMSIS 内核 + 启动文件 + stm32f10x.h
├── Library/                STM32F10x 标准外设库
├── System/                 Delay 延时
├── Hardware/               外设驱动（自写）
│   ├── AD.c                ADC 采样
│   ├── Key.c               按键
│   ├── LED.c               LED
│   ├── MPU6050.c           MPU6050 驱动（软件 I²C 时序部分为硬件 I²C2）
│   ├── OLED.c / OLED_Data.c  OLED 驱动 + 字库
│   ├── PWM.c               TIM2 PWM
│   ├── Servo.c             舵机角度 → CCR 映射
│   └── Serial.c            串口 + 接收状态机
└── User/
    ├── main.c              业务逻辑
    ├── stm32f10x_conf.h    库配置
    └── stm32f10x_it.c      中断入口
```

### 分层原则

| 层 | 是否依赖硬件 | 说明 |
|---|---|---|
| 业务逻辑（main.c） | 是 | 模式调度、数据流 |
| 驱动（Hardware/） | 是 | 唯一直接操作 SPL 的地方 |
| 硬件（SPL / CMSIS） | — | ST 官方库 |

**目标**：把滤波、映射这类纯数学逻辑从驱动里剥离出来，方便后续移植到 HAL 库或换 MCU。

## 编译与烧录

### 编译

1. 安装 **Keil MDK5**（需要装 `Keil::STM32F1xx_DFP` 器件支持包）
2. 打开对应目录下的 `Project.uvprojx`
3. `Project → Build Target`（`F7`）

编译产物在 `Objects/`，已被 `.gitignore` 排除，克隆后需要重新编译。

### 烧录

- **ST-Link V2**：`Options for Target → Debug → ST-Link Debugger → Settings` 勾选 `Reset and Run`
- **串口 ISP**：BOOT0 拉高，用 FlyMcu / STM32CubeProgrammer 通过 PA9/PA10 下载

### 蓝牙配置

两个 HC-05 需要**一主一从**配对：

```
# 进入 AT 模式（按住模块上的小按键上电，或 EN 拉高）
AT+ROLE=1          # 主机
AT+ROLE=0          # 从机
AT+UART=9600,0,0   # 两端波特率必须一致
AT+PSWD="1234"     # 配对码，两端一致
AT+RESET
```

主机会自动连接配对过的从机，连上后模块上的 LED 由快闪变**双闪**。

## 实测数据

### 循环周期

| 环节 | 耗时 | 占比 |
|---|---|---|
| ADC 双通道采样 | 11 µs | 0.07% |
| 角度映射 + 滤波 | ~2 µs | — |
| **串口发送 8 字节 @9600** | **8.3 ms** | **50%** |
| OLED 刷新（每 3 轮一次） | 平均 0.5 ms | 3% |
| `Delay_ms(8)` | 8 ms | 47% |
| **发送端合计** | **≈17 ms（59 Hz）** | |

### 端到端延迟分解（90° 阶跃）

| 环节 | 滞后 | 说明 |
|---|---|---|
| 发送端采样（平均半帧） | 8 ms | — |
| **发送端一阶低通 α=0.6** | **56 ms** | 95% 收敛需 3.3 帧 |
| 蓝牙 SPP 空口 | 15~30 ms | 协议栈决定，改波特率无影响 |
| **接收端限速 600°/s** | **150 ms** | 舵机物理极限 |
| 接收端循环延迟 | 5 ms | — |
| **合计** | **≈ 235 ms** | 小角度（5°）约 90 ms |

### 延时构成的结论

- **ADC 只占 0.07%** —— 加 DMA 对响应速度毫无帮助
- **蓝牙空口只占 5~10%** —— 提波特率的价值在于解放 MCU，不是降低空口延迟
- **两个大头是「滤波」和「限速」**，都是可调参数，不是硬件瓶颈

## 开发中遇到的问题

> 这部分记录的是真实的调试过程，踩过的坑比写过的代码更有价值。

### 1. `I2C_Send7bitAddress` 传的是 8 位地址

```c
/* ✗ 错误：以为参数是 7 位地址 */
I2C_Send7bitAddress(I2C2, 0x68, I2C_Direction_Transmitter);

/* ✓ 正确：SPL 内部会和 0xFE 相与，必须传完整 8 位地址 */
I2C_Send7bitAddress(I2C2, 0xD0, I2C_Direction_Transmitter);
```

现象：读不到任何数据，`I2C_WaitEvent` 一直超时。

### 2. MPU6050 丝印 ≠ 芯片型号

买的模块丝印写着 MPU6050，但读 `WHO_AM_I (0x75)` 返回 **0x70**，说明实际是 **MPU6500 系列**。

| WHO_AM_I | 实际芯片 |
|---|---|
| 0x68 | MPU6050 |
| **0x70** | MPU6500 |
| 0x71 | MPU9250 |

**影响**：两者的 `CONFIG (0x1A)` 寄存器位定义不同 —— MPU6050 的 `bits 5:3` 是 `DLPF_CFG`，而 MPU6500 的 `bits 2:0` 才是，加速度计低通在 `ACCEL_CONFIG2 (0x1D)`。

### 3. `atan` 除零导致读数爆炸

```c
/* ✗ az 接近 0 时除零，结果是 inf 或 NaN */
ThetaX = atan(AX_g / AZ_g) * 57.3f;

/* ✓ atan2f 内部判零，且保留象限信息 */
ThetaX = atan2f(AX_g, AZ_g) * 57.29578f;
```

### 4. 上电时舵机从 0° 扫到中位

滤波器初值是全局变量默认的 0，而真实目标角约 90°，于是上电后要爬几十个周期才到位。

```c
/* ✓ 进入模式时先采一次真实数据，再对齐滤波器 */
Sensor_Update();
S1_Filtered = S1_Angle;
S2_Filtered = S2_Angle;
```

### 5. 复制粘贴导致的变量名错误（反复出现）

`Servo_SetAngle2()` 写成 `SetAngle1()`、`Diff1` 用在第二轴、`S1_Filtered` 显示到 `S2` 的位置……

**这类错误编译器永远不会报**，症状是「某个轴完全不动」。

> 对策：写完任何「成对」的代码（X/Y、CH1/CH2、S1/S2），专门花 10 秒扫一遍两行的变量名是否对调。

### 6. 蓝牙单向收不到数据

现象：发送端能发，接收端收不到；但拔掉 HC-05 后 USB-TTL 能正常收到。

**根因：两个输出脚接到了同一根线上** —— STM32 的 PA9（推挽输出）和 HC-05 的 TXD（也是输出）短接，两个输出对顶，信号被拉成无效电平。

**教训**：串口是「交叉连接」—— 我的 TX 接你的 RX，**绝不能 TX 对 TX**。

### 7. 十六进制帧在串口助手里看起来是「空白」

`FF 02 03 04 05 FE` 全是不可打印字符，文本模式显示出来就是一片空白。

**对策**：串口助手切到 **Hex 模式**。

### 8. `static` 局部变量 vs `extern` 全局变量

```c
/* Serial.c */
void USART1_IRQHandler(void) {
    static uint8_t CurrentFrameMode;   /* 无链接属性，外部不可见 */
}

/* Serial.h */
extern uint8_t CurrentFrameMode;       /* 声明了一个全局的 */

/* main.c 使用了它 */
```

编译通过（作用域不同，各看各的），**链接才报错**：

```
Error: L6218E: Undefined symbol CurrentFrameMode (referred from main.o).
```

但**不能简单删掉 `static`** —— 那样它变成自动变量，每次进中断都重新分配，值会丢。正确做法是移到文件作用域：

```c
/* Serial.c 顶部 */
uint8_t CurrentFrameMode;              /* 全局定义 */
```

### 9. 状态机 `case 5` 漏写导致永久卡死

收满数据后 `RxState = 5`，但 `switch` 里 `case 5` 是注释掉的 → 之后所有字节都落空 → 状态机再也回不到 0。

**修复**：收满时直接完成并复位，不要引入无用的中间状态。

```c
if (pRxPacket >= CurrentFrameLen) {
    Serial_RxFlag = 1;
    RxState = 0;          /* 立刻回起点 */
}
```

### 10. 帧头顺序写反

发送端发 `AA 55 ...`，接收端状态机却先等 `0x55` 再等 `0xAA` → 永远进不了状态 2。

**教训**：两端的状态机要**对照着写**，最好画一张字节序列表贴在注释里。
